## 1. Data confirmed (no schema invented)

Read directly from `data_v3/*.json` before writing any code:

- `data_v3/retail_dataset.json` — **169** records. Fields: `id_actor, name, city, typology, typology_detail, channel, canal_secundario, physical_exhibition, exhibition_evidence, price_range, price_signal, service_scope, email, phone, address, main_channel, source_language, source_url, materials_brands_mentioned, key_messages, raw_notes, data_source, tool_used, priority_candidate_v2, _source_file`.
- `data_v3/proyectos_dataset.json` — **83** records, identical field set to retail (confirmed by inspection — no separate schema branch needed in code).
- `data_v3/new_tashkent_projects_v3.json` — **20** records. Fields: `project_name, developer, location, status, scale, estimated_delivery, source_url, notes`.

Counts verified with `grep -c '"id_actor"'` / `'"project_name"'` against the raw files: 169 / 83 / 20. Matches the prompt exactly, so datasets are used as-is, unmodified.

`UZ_partner_intelligence_new/data.js` is generated by direct byte concatenation of the three JSON files behind `const RETAIL_DATA = …`, `const PROYECTOS_DATA = …`, `const DEVELOPMENTS_DATA = …` — no manual transcription, so it cannot silently diverge from `data_v3`. Regenerate it by re-running the same concatenation if `data_v3` ever changes.

Both actor datasets share one schema, so the app has a single rendering/filtering/scoring path parameterized by `channel: 'retail'|'proyectos'`, not two parallel code paths.

## 2. Architecture

```
UZ_partner_intelligence_new/
  index_R_P.html      cover: channel + proposal picker, brand module, EN/RU
  proposal_A.html      Executive Intelligence (light) — shares DOM ids/structure with B
  proposal_B.html      Market Command Center (dark) — shares DOM ids/structure with A
  base.css             structural CSS shared by both proposals (grid, nav band, chips, drawer, table, responsive, focus states)
  proposal_A.css       Proposal A visual tokens + composition deltas
  proposal_B.css       Proposal B visual tokens + composition deltas
  data.js              RETAIL_DATA / PROYECTOS_DATA / DEVELOPMENTS_DATA (generated, see §1)
  app-core.js          i18n dictionary, state, filters, scoring model, positioning-map layout algorithm, drawer builder, CSV export, coverage/competitive computations
  assets/              Cosentino brand images (placeholders documented until fetched — see assets/README.md) + screenshots
  tests/test-runner.html   in-browser assertions (counts, unique ids, map min-separation, filter/KPI sync)
  README.md
```

Both proposals load `data.js` then `app-core.js` then call `AppCore.mount({ theme: 'A'|'B' })`. They share the same element IDs and the same render functions; only `proposal_A.css` / `proposal_B.css` and a body class (`theme-a` / `theme-b`) differ, plus a few theme-conditional composition branches inside `app-core.js` (e.g. Proposal B's map legend sits in a side rail instead of a footer strip). This satisfies "share data, filter logic, accessibility and functionality; only the visual direction/composition differs" without maintaining two logic trees.

State lives in one object (`AppCore.state`): `lang`, `channel`, `proposal`, `view`, `filters{search,city,typology,priority,price,exhibition,competitive,secondary}`, `selectedId`. `lang` and `proposal` persist via `sessionStorage` (spec: "durante la sesión"). Channel/view/filters reset per navigation, as expected for a fresh drill-down.

## 3. Priority / scoring model ("About the model")

Transparent, deterministic, documented in-app (not presented as a sales fact). Per record, weighted 0–100 sum of normalized sub-scores, channel-aware:

**Retail** weights: physical exhibition confirmed (25), typology fit for Silestone/Sensa countertops — Kitchen/Kitchen&Bath/Showroom/Interior Designer Retail score higher (20), price positioning Medium/High favored over Low (15), service scope breadth — Design+Install+Supply > Design-only (15), competitive/material signal present (15), contact + source evidence quality (10).

**Proyectos** weights: New Tashkent / equivalent-scale linkage in notes/location (20), typology fit for Dekton (Facade Installer/Developer/Architecture Studio/Contractor score higher) (20), status & horizon — under construction/near-term favored over "announced/no date" (15), specification/scale signal in `service_scope`/notes (15), competitive/material signal (15), contact + source evidence quality (15).

Each factor's contribution is kept and surfaced as the `why` breakdown shown in the drawer and the shortlist ("Why now"). Tiers: High ≥ 70, Medium 40–69, Low < 40. The legacy `priority_candidate_v2` field is shown as provenance ("prior-pass flag") but does not feed the score, so the model is reproducible from the visible fields alone.

## 4. Positioning map — collision avoidance

- Y axis: priority score (0–100) — "priority/fit".
- X axis: price/positioning tier (Low/Medium/High) fractionally offset by service-scope breadth within the tier, so points with the same price tier still spread out — "positioning / service breadth".
- Both axes are labelled in the UI with a one-line legend explaining what they encode.
- Layout algorithm (`layoutPoints` in `app-core.js`): compute each point's true (x,y) in pixel space from the model above, sort by a stable key (id), then place points in that order with a deterministic spiral search — if a candidate position is within `MIN_DIST` (24px desktop / 18px narrow) of any already-placed point, step outward along a fixed-increment spiral until clear, clamped to the plot bounds. True value is preserved as `trueX/trueY` for the tooltip/drawer; only the *drawn* position is nudged, and the nudge is bounded (documented in-UI as "positions are nudged slightly to avoid overlap; exact score shown on hover/selection"). Re-run on every filter change so the visible subset is always collision-free.
- Hit-area per point is >= 26px (drawn marker can be smaller), via a transparent padded `<circle>`/button wrapper, so dense clusters stay clickable.
- `tests/test-runner.html` asserts, for the full dataset and after representative filters, that the minimum pairwise distance between rendered points in the same view is >= the configured minimum.

## 5. Filters

Chip/pill controls (`role="group"` + `aria-pressed` per chip), combinable, with a single `Reset`. Retail chip groups: city, typology, priority tier, price range, physical exhibition (confirmed/not confirmed/not determinable — never collapsed to a binary), competitive signal (has `materials_brands_mentioned`), secondary channel (when `canal_secundario` present). Proyectos: same shape, typology list swapped to the Proyectos categories actually present in the data. Free-text search matches name/address/phone/email/materials/key_messages. KPI tiles double as filter shortcuts (total → reset+list, high priority → priority filter + shortlist view, showroom → exhibition=confirmed + list view, cities → Coverage view) and are real buttons (keyboard operable, `aria-label` states the action). Mobile: filters collapse into an accessible drawer/panel triggered from the nav band.

## 6. Right-hand drawer

Opens on click/Enter/Space from map point, table row, or shortlist card. Closes on button, `Escape`, or overlay click; focus moves into the drawer on open and back to the trigger on close. Shows every field listed in the prompt, split visually into **Verified evidence** (dataset fields) vs **Commercial recommendation** (the model's tier + a templated next-action sentence keyed off typology, explicitly labelled as a suggestion). Missing evidence renders the literal `Not evidenced in current research` / RU equivalent — never blank, never invented.

## 7. Other views

- **Account list**: sortable table, horizontal scroll on narrow widths, respects all active filters.
- **Priority shortlist**: only High/Medium tier accounts, each card shows score, "Why now" (top-2 scoring factors in plain language) and "Next action" (same template as the drawer).
- **Coverage**: compact matrix — rows = city, columns = typology/price/exhibition counts — bars, not a card grid.
- **Competitive landscape**: aggregates `materials_brands_mentioned` into named competitor/material tags with counts by typology/city; clicking a tag filters the account list to matching records.
- **Project developments** (Proyectos only): separate table/detail over `DEVELOPMENTS_DATA` (own filters: status, developer, horizon-from-`estimated_delivery` text), own drawer variant, no priority score fabricated — only a plain-language "commercial timing read" clearly marked as a reading, not a fact.

## 8. i18n

Single dictionary object in `app-core.js` (`I18N.en`, `I18N.ru`), one `t(key)` lookup used everywhere, no duplicated markup per language. Proper nouns, brand names, emails, URLs and raw source quotes are never translated; original-language source content gets a small "source language: …" tag instead.

## 9. Export

CSV export always reflects the current channel + active filters (actors) or the Project developments filters (developments), UTF-8, RFC4180-style quoting/escaping for commas/quotes/newlines.
